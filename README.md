# trial-review

수정안·변경안·정책안을 **재판 형식**으로 평가하는 Claude 플러그인입니다. 여러 안건 중 무엇을 적용할지, 어떤 순서로 할지를 직무별 배심원 투표로 가립니다.

- 재판장은 실무 PM/컨펌매니저이고, 배심원은 서로 다른 직무입니다. 안건 성격에 맞게 편성합니다.
  - 화면·문구 중심 코드: PM, UX, FE, BE, QA, A11y, CS, Data
  - 서버·DB·API·인프라: BE, DBA, 보안, SRE, QA, PM, CS, Data
  - 정책·기획: PM, 영업, 재무, 법무, 운영, CS, 대상 사용자, Data
  - 안건이 1건이면 쟁점에 맞는 4명으로 줄입니다.
- 평가는 두 번입니다. 1차는 적용 전에 텍스트만 보고, 2차는 적용해 관찰한 뒤 합니다. 적용하지 않았거나 관찰하지 못한 안건의 2차 평가는 만들지 않고 "2차 미실시(사유)"로 표시합니다.
- 모든 배심원이 모든 안건에 ○(찬성), ×(반대), −(기권)로 투표하고, 다른 안건과 함께 적용될 때의 충돌·중복·시너지도 봅니다.
- 결과는 **채택 후보 / 조건부 / 보류 / 기각 / 판단 불가**로 나누고, 상태와 찬성 비율 순서의 적용 순위 표로 출력합니다. 이미 반영된 안건은 "이미 반영", 바꿀 내용이 없는 안건은 "내용 요청"으로 따로 표시합니다.

## 판정 기준

| 상태 | 기준 |
| --- | --- |
| 채택 후보 | 찬성이 배심원의 75% 이상 (8명이면 6표) |
| 조건부 | 60% 이상 75% 미만 (8명이면 5표). 조건을 함께 적습니다 |
| 보류 | 그 미만 |
| 기각 | 찬성이 0표이고 반대가 절반 이상 |
| 판단 불가 | 기권이 절반 이상 (판단할 자료가 없음) |

- **차단급 반대:** 보안(인증 우회, 평문 저장, 개인정보 노출 등), 데이터 손실, 접근성, 법적·재무적 피해는 문서나 코드의 해당 줄 인용이 있을 때만 인정하며, 상태를 한 단계 낮춥니다. 원본을 열기 전 인용은 "미확인"으로 표시합니다. 사용자의 위험 판단·압박 발언은 근거가 아닙니다.
- **증거 기준:** 안건이 요구하는 모든 항목이 확인될 때만 "이미 반영"으로 봅니다. README·주석 같은 작성자의 자기 서술은 "(자기 서술)"로 표기하고, 코드·설정을 직접 열어 확인한 것만 확인으로 인정합니다.
- **반영 기준:** 채택 후보만 바로 반영합니다. 조건부는 조건 충족 확인 뒤, 보류·기각·판단 불가는 안건별로 명시적 확인을 받은 뒤에만 반영합니다. "묻지 말고 다 적용" 같은 포괄 지시는 채택 후보에만 효력이 있습니다.

## 안건 수·유형에 따른 방식

- 6건 이상이면 직무별 표 대신 요약 형식을 씁니다. 25건 이상이면 상위 12건만 상세히 적습니다.
- 코드가 아닌 정책·기획 안건은 "적용"을 "시범 계획(범위, 성공 기준, 되돌리는 법)"으로 바꾸고, 관찰 데이터(기준선·기간·표본 수)가 있으면 2차를 합니다.
- 이미 적용된 안건(소급), 읽기 전용 요청, 영어 요청, 요청이 안건 번호를 지정한 경우 등 드문 경우는 `references/edge-cases.md`를 따릅니다. 출력 형식 예시는 `references/example.md`에 있습니다.

## 설치

### Claude Code (CLI)

```
/plugin marketplace add PROMISE282/trial-review-plugin
/plugin install trial-review@promise282-tools
```

이미 설치했다면 `/plugin` 화면에서 마켓플레이스를 업데이트한 뒤 플러그인을 갱신합니다(1.1.0부터 새 규칙이 적용됩니다).

### Claude Desktop

Claude Code 탭의 플러그인 화면에서 마켓플레이스로 `PROMISE282/trial-review-plugin`을 추가한 뒤
`trial-review`를 설치합니다.

### ChatGPT / Codex 등 OpenAI 도구 (실험적)

이 플러그인의 실체는 `SKILL.md`와 `references/` 파일이며, 스크립트나 훅은 없습니다. `.claude-plugin/` 매니페스트만 Claude 전용이라, `SKILL.md` 형식(Agent Skills)을 지원하는 도구에서는 스킬 폴더만 복사해 쓸 수 있습니다.

- **Codex CLI:** `plugins/trial-review/skills/trial-review/` 폴더를 통째로 스킬 폴더(예: `~/.codex/skills/`)에 복사합니다. 경로는 Codex 버전에 따라 다를 수 있으니 해당 도구의 스킬 문서를 확인합니다.
- **ChatGPT 웹(커스텀 GPT):** 스킬 폴더를 직접 읽지 못할 수 있습니다. 이 경우 `SKILL.md` 본문을 지침에 붙여 넣되, 지침 글자 수 제한(약 8,000자)을 넘으면 `SKILL.md`와 `references/*.md`를 지식 파일로 올리고 지침에는 "지식 파일의 `SKILL.md`를 따른다"고 적습니다.
- Claude 전용 표현(스킬 호출 이름, 도구 이름)은 다른 도구에서 의미가 다를 수 있습니다. 이 방법은 아직 OpenAI 도구에서 시험하지 않았습니다.

## 사용

대화에서 "재판 형식으로 판단해줘", "배심원 투표로 우선순위 매겨줘", "찬성 비율로 순위"처럼 말하면 스킬이 자동으로 쓰입니다. 영어로는 "trial review", "jury vote"도 인식합니다.
직접 부르려면 `/trial-review:trial-review`를 입력합니다.

## 한계

- 배심원 투표는 한 모델이 직무 관점을 흉내 낸 **모의 투표**이며 독립 표본이 아닙니다. 실제 사람의 투표나 통계적 근거가 아닙니다.
- 기술 결함 검출은 코드 리뷰와 CI의 몫입니다. 이 스킬은 그 결과가 있으면 인용하고, 없으면 "기존 검증 없음"을 한계에 적습니다.
- 규칙은 같은 모델로 평가자를 흉내 내는 시험으로 다듬었으며, 실제 사용자 연구를 거치지 않았습니다. 소수의 문서(UI 개선, 인프라 조사, 가상 정책안)로만 확인했습니다.

## trial-review-personas (시험판)

`trial-review`에 **직무 페르소나**와 **안건별 배심원 배치**를 더한 시험판입니다. `trial-review`와 버전과 배포를 따로 관리하며, 이 브랜치(`personas`)에 있습니다. 사용자가 "trial-review-personas", "페르소나 재판", "페르소나 배심원"이라고 말할 때만 쓰이고, 일반 "재판해줘"에는 `trial-review`가 쓰입니다.

```
/plugin install trial-review-personas@promise282-tools
```

- 배심원 직무마다 판단 기준(`references/personas.md`)을 둡니다. 출처는 사람이 확인하는 용도로 `references/personas-sources.md`에 분리했고 평가 중에는 읽지 않습니다.
- PM은 모든 안건에 고정하고, 나머지는 안건의 쟁점 종류(화면·문구 / 서버·DB·API / 정책·기획)에 따라 안건마다 고릅니다. 대상 사용자는 일반 사용자(비개발자), 개발 공부하는 사람, 실무 개발자 중 안건의 실제 사용자에 맞춰 고르고, 일반 사용자는 전문 지식이 필요한 안건에서 기권합니다.
- 법무 관할은 기본이 한국이며, 요청이나 자료에 다른 관할 신호가 있으면 추가합니다. 모호하면 머리말 한계에 "법무 관할: 한국 가정"이라 적습니다.
- 코드를 직접 열어 확인한 것만 인용하고, "없다"고 단정하기 전에 대체 수단을 확인하며, 코드의 커밋 상태는 `git status`·`git diff`를 본 경우에만 씁니다.

### 시험 방법

- **안건:** 같은 8건(A~H)을 모든 시험에 썼습니다. A 컨트롤 높이 44px 통일, B 입력창 `outline: none` 7곳 제거와 포커스 링, C URL에 검색어·필터 보관, D 브라우저 저장 모드 유지, E 모바일 메뉴 Esc·포커스 복귀(이미 반영된 안건), F 업로드 API 로그인 검사 제거(차단급), G 수천만 행 테이블 컬럼 타입 변경(`ALGORITHM`·`LOCK` 미지정), H 탈퇴 계정 제출 코드 무기한 보존(차단급). 요청은 "수정하지 말고 1차만 해줘"로 고정했습니다.
- **실행:** 한 조건을 서브에이전트가 스킬 파일을 읽고 재판을 수행하는 방식으로 2~5회 돌렸습니다. 토큰은 서브에이전트가 보고한 한 회차 총 토큰입니다.
- **채점:** 조건을 숨기고 출력을 섞은 뒤(블라인드) 독립 채점자 2명이 각각 정방향·역방향 순서로 채점했습니다. 아래 표는 채점자 2명의 평균입니다.
- **정답표:** A·B·C는 채택 후보 또는 조건부. D는 조건부·보류·기각(소실 안내가 없는 브라우저 저장 방식이므로 채택 후보면 불일치). E는 "이미 반영"과 근거. F·H는 차단급 표시와 보류·기각·판단 불가. G는 조건부·보류·기각. G 안건은 처음에 기각을 불일치로 보다가 허용으로 바꿨습니다(첫 시험에서는 두 기준을 모두 적었습니다).
- **지표:** 구체성(직무 기준이나 자료의 줄을 인용한 서로 다른 근거 수), 환각(자료에 없는 사실, 없는 줄·조문 인용, "없다" 오단정, 개수 오기입, 코드 커밋 상태 오단정의 수), 정답 일치(8건 중 일치 건수), 결정 품질(0~5), D 안건을 조건부 이하로 낸 횟수.

### 1. 원본 대 시험판 (0.1.0, 0.1.1)

| 지표 | 원본 | 시험판 v1 (0.1.0) | 시험판 v2 (0.1.1) |
| --- | --- | --- | --- |
| 구체성 | 6.75 | 약 10 | 10.75 |
| 환각 | 0 | 1.25 | 0 |
| 정답 일치 (완화 기준) | 7.5 | — | 7.5 |
| 정답 일치 (G 기각 불일치 기준) | 7.5 | 6.5 | 6.5 |
| 채택 후보 수(편향) | 3.0 | 3.0 | — |
| 토큰 | 약 77.3k | — | 약 86.4k (+12%) |

- v1은 구체성은 높았지만 환각이 늘고 정답 일치가 낮아 기준을 넘지 못했습니다. v2는 인용 규칙을 추가하고 출처를 분리하며 근거를 4개 이내로 줄여 환각을 0으로 되돌렸습니다.
- `personas.md`를 4,200바이트 줄였을 때 총 토큰은 1.6%만 줄었습니다. 한 번의 평가에서 토큰 대부분은 스킬 파일이 아니라 저장소 파일 읽기와 출력입니다.

### 채점 방식

**기존 방식:** 구체성(서로 다른 근거 수), 환각(오류 건수와 경미 건수), 정답 일치(상태가 정답표 허용 범위인 안건 수), 결정 품질(0~5의 총평)을 채점자가 정의에 따라 판단합니다. 사실 확인은 채점자가 파일을 직접 열어 합니다.

**개선 방식:** 기존 방식에서 다음 문제를 찾아 고쳤습니다.

| 기존 방식의 문제 | 개선 |
| --- | --- |
| 정답표가 없어 같은 서술의 환각 여부가 채점자마다 갈렸습니다(예: `var(--control-height)`를 "9곳"이라 쓴 서술을 한 채점자만 환각으로 셌지만 실제로는 9줄이 사실) | 채점자에게 **사실 정답표**를 제공하고, 표에 있는 사실은 다시 검색하지 않게 했습니다. 표에 없는 사실만 최대 3번 확인합니다 |
| 구체성이 채점자마다 눈금이 다르고 길수록 유리합니다 | **검증된 근거 수(V)**: 안건당 4개까지만 세고, 검증됨·틀림·미검증으로 구분해 정밀도(V/T)를 함께 냅니다 |
| 환각의 중대도와 헤지("확인하지 못함")를 세는 기준이 불명확했습니다 | **가중 오류 지수**: 창작 3점, 정답표와 반대인 단정 2점, 허용 범위 밖의 개수·줄 번호 1점, 헤지 0점입니다. 판결이 헤지를 "없다"의 전제로 쓰면 2점입니다 |
| 정답 일치는 D 안건 한 건이 좌우하고, 한 단계만 어긋나도 0점입니다 | **상태 점수**: 허용 상태 1점, 한 단계 어긋나면 0.5점입니다 |
| 결정 품질 총평은 주관적이고 정확도와 섞입니다 | **체크리스트 5개**(예/아니오): 반대 이유의 구체성, 채택 후보의 확인 조건, 판결과 표의 일관성, 미해소 반대의 반영, 기각·보류 안건의 재상정 조건 |

개선 방식으로 채점한 뒤에는 환각 수와 상태 점수가 정방향·역방향 채점자 사이에 10개 출력에서 모두 같았고, 품질은 기존 방식이 7개 출력에서 달랐던 반면 개선 방식은 3개에서 달랐습니다. 채점 한 번의 토큰은 기존 방식이 119~121k, 개선 방식이 116~117k로 큰 차이가 없었습니다.

**사실 정답표(개선 방식에 쓴 값):** `tokens.css:104`의 `--control-height: 44px`, `var(--control-height)` 사용 9줄(`min-height` 7 + `width`·`height` 2), `outline: none` 7곳(452·1490·4171·6916·7138·7277·7302줄)에 모두 대체 포커스 표시 존재(7302→7319줄, 6916→`::after`, 1490→1492줄 등), `LocalStorageNotice` 사용 8개 페이지, `useUrlFilters`는 `AnalysisPage.tsx` 한 곳, Esc 처리는 HEAD에 이미 커밋됨(작업 트리 201~203줄), 업로드 API 서버 코드는 저장소에 없음.

### 유의사항

- 모든 시험은 같은 모델이 평가자와 채점자를 맡았고, 사람의 평가를 거치지 않았습니다. 정답표는 시험 설계자가 만들었고 G 안건의 허용 범위를 시험 도중 한 번 바꿨습니다.
- 안건은 8건 하나뿐이고 조건당 표본은 2~5회입니다. 소수점 단위 차이는 편차 안일 수 있고, 표본을 늘리면 초기 이득이 줄어드는 경향이 있었습니다.
- 채점 묶음마다 채점자와 눈금이 달라 **서로 다른 묶음의 절대값은 비교할 수 없습니다.** 같은 묶음 안의 상대 비교만 의미가 있습니다. 같은 묶음 안에서도 채점자마다 절대값이 달랐습니다(한 채점자가 다른 채점자의 약 1.3배를 주기도 했습니다).
- 토큰은 서브에이전트 한 회차의 총 토큰이며 원본 값(약 77.3k)은 초기 2회 측정입니다. 한 번의 평가에서 토큰 대부분은 저장소 파일 읽기와 출력이어서, 스킬 파일을 줄여도 총 토큰은 크게 줄지 않습니다.
- D 안건(브라우저 저장 모드)은 8명 중 7명이 찬성하는 일이 잦아 표수 기준만으로는 채택 후보가 됩니다. 이 안건을 조건부로 내리려고 규칙을 맞추면 시험 안건에만 맞춘 과적합이 되므로 규칙으로 고정하지 않았습니다.
- 남은 오류는 주로 `outline: none` 7곳 중 `.solve-resizer`(7302줄)나 `.judge-resizer`(6916줄)처럼 대체 포커스 표시가 멀리 떨어진 규칙에 있는 경우를 놓쳐 "없다"고 쓰는 것입니다.
